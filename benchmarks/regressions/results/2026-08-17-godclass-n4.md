## What this measures

One of three planned axes for validating the god-class extraction playbook — the other two, process adherence and output quality, aren't built yet (see "What this run led to" below). This axis is the fully automatic one: does the extraction break anything that wasn't supposed to change?

## Fixture

`../fixture/` — a small but structurally real god-class: five unrelated flows (`calculateLoyaltyBonus`, `calculateShippingFee`, `applyDiscountCode`, `generateInvoiceSummary`, `processRefund`), a `requireCustomer` helper shared by four of the five — including the flow being extracted, which is the playbook's Step 0/5 "shared use" case — and one deliberately failing test documenting a pre-existing, out-of-scope bug in `processRefund` (the fee comparison is inverted). Baseline state: 18 tests, 17 green, 1 red.

## Task

Extract `calculateLoyaltyBonus` into its own `LoyaltyBonusService`, same package. `calculateShippingFee` must not change. Keep the existing suite behaving the same way, including the one known-red test. Identical prompt for both arms (see `../task.md`); the only difference is one line: the with-skill arm is told to use the `software-design-principles` skill's playbook, the baseline arm is told explicitly not to consult any skill.

## Method

Headless Claude Code subagents, four seeds per arm (eight runs total), each working in its own isolated git-inited copy of the fixture. Scored automatically by `../score.sh`. The raw `mvn test` exit code is *not* the pass criterion — it's expected non-zero even on a perfect run, because the known-red test must stay red. The scorer reads the surefire XML per test and checks two things separately: whether anything *other than* the known-bug test started failing (a regression), and whether the known-bug test itself is still failing, unchanged, versus silently passing (flagged as scope creep, not scored as a regression, since nothing broke — something out of scope just quietly changed).

## Interpretation

No differentiation on this axis, at this task's difficulty. That's a real result, not a null one: a single-flow extraction out of a five-method class, where the target flow already has full test coverage, isn't hard enough to make a reasonably capable baseline agent break something. The regressions axis likely saturates before showing a gap here — surfacing one probably needs a harder task (more shared dependencies, a bug fix riding along, a flow with zero pre-existing tests) rather than a larger N of the same task.

## What differed, outside this axis

Not part of the regressions score, but consistent across every transcript:

- **4/4 with-skill runs** duplicated the shared `requireCustomer` helper with an explicit `REFACTOR NOTE` — what's duplicated, why, and the removal criterion. Step 5 of the playbook, followed by name in every single run.
- **0/4 baseline runs** did this. They made the same underlying technical call (duplicate the helper rather than move it, since three other flows still need it) but never documented why or when to consolidate.
- With-skill runs added 5–7 new tests each (23–25 total after); baseline runs added 0–4 (18–22 total after). With-skill runs explicitly named guard-branch cases (a purchase below the lowest threshold, a tier absent from the rate table) in their own reports; baseline runs didn't call these out as deliberate.

These are exactly the two axes planned next. This run wasn't designed to score them, but the signal is already visible and consistent enough to be worth building on.

## What this run led to

- Found and fixed a real gap in the playbook itself, spotted by inspection while writing this fixture, not by a benchmark failure: no explicit rule against starting a second flow before the first one's Definition of Done is fully checked off. A god class with dozens of flows left invites "just one more while I'm in here" — exactly the big-bang risk the playbook exists to prevent. Added an explicit "one flow per pass" rule (commit `cdc8f35`).
- Identified this fixture's main limitation for a follow-up: the extracted flow already had full test coverage going in. The next variant needs a flow with **zero** pre-existing tests and an undocumented bug, to test something this run couldn't: does the skill write a characterization test that captures current behavior (bug included, per principle 19), or does it "helpfully" assert what it assumes is correct — silently fixing something out of scope?

## Limitations

- Single task shape: one flow, one shared helper, one untouched pre-existing bug. Not yet tested: a flow with no tests at all, a task that bundles an explicit bug fix, or a class with more than one kind of shared dependency.
- Single model, no cross-model comparison.
- N=4 is enough to catch a consistent behavioral difference, not a rare one — the same tradeoff ponytail's own benchmark makes, for the same reason (stability signal, not exhaustiveness).
- Raw per-run transcripts and git commits lived in a scratch directory that isn't preserved — only the aggregated scores and the qualitative notes above survive here.
