# Partial N=4 scale-up — 3 principles, 2026-08-22

Not a full N=4 run across all 20 principles — that's ~160 more agent runs,
deliberately not attempted in one batch (token-consumption discipline, see
`benchmarks/README.md`). This is a targeted scale-up of the 3 principles
that showed the most signal at N=2: DRY, CQS, and Fail Fast (05-dry.md,
07-cqs.md, 14-fail-fast.md), adding seed3 and seed4 on top of the existing
seed1/seed2 data from
[the 2026-08-19 report](2026-08-19-principles-and-rerun.md). 24 new runs
total (3 principles × 2 cases × 2 arms × 2 seeds), same methodology: haiku
for Case A (recall), sonnet for Case B (calibration), baseline told
explicitly not to consult any skill, with-skill told to use it.

## Results

### Fail Fast — fix confirmed stable

Both seed3 and seed4, both arms, both cases: clean. Case B (the one that
had a repeated false-positive at N=2, root-caused and fixed by adding
`@Valid` + an explanatory comment to the case file, not the skill) now
passes reliably across two fresh seeds it was never tested against before
today. This is the strongest evidence yet that the miss really was a
case-file defect, not a skill or model limitation — a fluke fix would have
cracked again by the second new seed.

One borderline: seed4's Fail Fast Case B baseline called the manual
`items().isEmpty()` check "correct, just slightly redundant" — didn't
recommend removing it (no false Fail Fast flag), but the word "redundant"
is a hair closer to a miss than the other 7 runs. Logged as-is rather than
smoothed into a clean pass.

### CQS Case A baseline — investigated: real ~50% recall, not a systematic miss

Seed3 and seed4 both missed the actual violation (`hasSufficientFunds`
promising a pure query but writing to an audit log as a side effect) —
instead flagging real but beside-the-point issues: `double` for currency,
missing null checks, a missing constructor. That looked like a new,
repeatable miss, so two more seeds (seed5, seed6) were run to check.
Seed6 caught it cleanly, naming "command-query separation" outright;
seed5 missed it again, same generic-checklist pattern.

**Full picture across 6 seeds**: baseline hit seed1, seed2, seed6 and
missed seed3, seed4, seed5 — **3/6 (50%)**, not the 0/2 the first two new
seeds suggested. With-skill is 4/4 on the seeds it was run against (no
with-skill runs at seed5/seed6, since those two were baseline-only,
launched specifically to size the baseline rate).

**What the misses have in common, read across all 4 losing transcripts**:
every one opens with the same short list of well-known, syntactic Java
review idioms — `double` for currency, missing null guards, missing
input validation, sometimes a missing-constructor compile-error read —
and never gets to "the method name promises a pure check but the body
writes to a log." The 2 hits, by contrast, name the mismatch directly
and immediately ("Flag: Side effect in a query method... violating
command-query separation"). Working hypothesis, not yet proven: CQS
violations require reading method-name-vs-behavior semantics, which
isn't a standard "common Java pitfalls" idiom the way `BigDecimal`-for-
money is — so an unprimed haiku reviewer's checklist reflex crowds it out
roughly half the time. With-skill's explicit, named list of 20 principles
(CQS among them) directly compensates for that gap by making it something
to check for rather than something to notice unprompted. Consistent with
this project's existing thesis (the skill's value is structure/naming,
not raw capability), just showing up on recall variance here instead of
the calibration-precision axis already documented.

Not settled: 3/6 vs. 4/4 with-skill is still a small sample, and the
mechanism above is read off 4 transcripts, not tested by varying the
snippet to isolate the semantic-vs-syntactic distinction. Worth a
dedicated small experiment (e.g. a case where the syntactic smells are
removed, leaving only the CQS mismatch) rather than more seeds on the
same snippet, if this gets picked up again.

### CQS Case B — case file confound, not a skill/model issue

All 4 new runs (both arms, both seeds) never explicitly addressed the
calibration point being tested (does `metrics.increment` inside a query
count as a CQS-breaking side effect). Instead, every single run found and
focused on other real bugs in the snippet: `cache.put(id, loaded)` caching
a null on a miss, a get-then-put race condition, and (in the baseline
prompts, which don't get the surrounding class context) undeclared
`metrics`/`repository` fields reading as a compile error.

This is the same shape of problem the Fail Fast Case B fix addressed
2026-08-19: a case file with enough *other* legitimate things to say that
the one specific point being measured gets silently skipped rather than
explicitly reasoned through. Per the grading rubric's own standard
("silently missing it because it never looked is not the same as
correctly deciding it's fine"), none of these 4 runs cleanly demonstrates
correct calibration — even though none of them incorrectly flagged CQS
either. The case doesn't currently isolate the thing it's meant to test.

**Fixed same day**: declared `repository`/`metrics` as fields (removed
the "undeclared field" read) and added a comment addressing the
null-caching and race-condition tangents as accepted tradeoffs, same
shape as the Fail Fast fix. Verified with one fresh baseline + with-skill
run: both now explicitly reason through the metrics point instead of
being pulled toward the other bugs — baseline: "incrementing on miss
regardless of outcome is correct"; with-skill: "I considered it and it's
correct." One run each, not a full reseed of Case B — worth folding into
the next N=2/N=4 pass rather than treated as fully re-validated yet.

### DRY Case B with-skill — investigated: real ~33% miss rate, and it's calibration, not a case-file problem

Clean on seed1, seed2, seed3. Missed on seed4. Two more seeds (seed5,
seed6) were run to check whether that was noise: seed5 clean, seed6
missed again. **Full picture across 6 seeds: 4/6 (67%) correct**, 2
misses — a real rate, not a single fluke.

Unlike CQS Case B, this case file has nothing wrong with it — no
undeclared fields, no competing bugs, nothing to get distracted by. Both
misses read the exact same two 1-line classes as the 4 hits and reasoned
their way to the wrong conclusion on a genuinely close call. The 2 misses
share a tell: seed4 asserts "an obvious third [variant] on the way" —
a growth signal invented, not present in the snippet — and seed6 concedes
"only two near-identical one-liners" but still calls it "the DRY smell
here" needing a fix (a lighter one than a full interface, but a fix). The
4 hits, by contrast, explicitly invoke Rule of Three / YAGNI and stop.

This is the one principle-precision miss in this whole investigation that
isn't explained by a fixable case-file defect — it's the skill sometimes
over-applying DRY on a case designed to test exactly that failure mode
(principles.md's own stated risk: "the most common mistake, once you know
a principle, isn't ignoring it — it's overusing it"). Nothing to fix in
the case file; this is a real, if partial, gap in the skill's own
calibration guidance for DRY specifically.

**Same-day attempt at a fix, then a deeper correction after a real
reseed**: `principles.md`'s DRY section stated "same knowledge, not
necessarily same text" but never its inverse — that similar *text/shape*
isn't necessarily the same knowledge, which is what both misses seemed to
get wrong. Added a concrete test: "would a future change to one require
changing the other, for the same reason?" First verification (seed7,
seed8, 2 runs): both held back from a hard flag — looked like a pass.

A proper reseed (4 more: seed9-12, bringing the post-fix sample to 6)
changed the read entirely. All 6 held back from a hard flag — 6/6 on the
surface. But rereading all 6 transcripts for *why*, not just *what*: not
one of them uses the new test, or anything resembling "these are
different business rules that happen to look alike." Every single one
reasons the same way the original passing runs did before the edit
today: "real duplication, but only two instances — rule of three isn't
met, wait for a third." That's also, on rereading, what seed3 and seed5
(both logged as clean earlier today) actually said — "real but
sample-size-one," "DRY-lite... premature." The edit didn't get adopted
because the model already has a strong, well-trodden rule-of-three
instinct that's easier to reach for than the knowledge-vs-shape
distinction being asked for, fix or no fix.

**The more useful finding sat underneath the hit/miss count, not in it**:
rule-of-three reasoning gets the *current* answer right by coincidence,
because the snippet happens to show exactly 2 instances — sitting right
on the "not yet 3" side of the heuristic's own threshold. It doesn't
generalize the way the case wants it to. If a third similarly-shaped
email builder appeared (`GoodbyeEmailBuilder`, say), rule-of-three
reasoning would flip to *recommending* an abstraction — while the actual
DRY answer would still be "no," since a third coincidentally-similar,
still-unrelated business rule is exactly as much a non-duplication as
the first two. The hit/miss tally recorded today measured the surface
action (flag or not), which rule-of-three reasoning gets right at n=2 for
the wrong reason — not whether the underlying reasoning would survive the
case actually being extended. That's a sharper, harder problem than "the
wording is missing a sentence," and not one a single edit fixes.

### The rule-of-three trap, tested directly — hypothesis confirmed

The prediction above (rule-of-three reasoning would flip to recommending
abstraction at a third instance, even though a third coincidentally
similar, still-unrelated business rule is exactly as much a
non-duplication as the first two) is testable directly: add a third
class, same shape, still a different business rule.

```java
public class GoodbyeEmailBuilder {
    public String subject(String name) { return "Sorry to see you go, " + name + "."; }
}
```

Not a scored case-file addition — a quick 4-run exploratory check
(with-skill only, sonnet) of `WelcomeEmailBuilder` +
`ReminderEmailBuilder` + this third class, together.

**Confirmed, cleanly, 4/4**: every run reasoned about the code purely in
terms of instance count against a shifting threshold, never in terms of
whether the three subject lines actually encode the same knowledge (they
don't — welcome, reminder, and goodbye are three unrelated rules that
happen to share a "greeting + name" shape). Two hard-flagged it outright
("Duplication is the real issue... flag as DRY"; "textbook duplication...
flag it as 'watch for a 4th case'"). Two held back, but by moving the
goalpost rather than recognizing the pattern — one explicitly says three
one-liners is "exactly the '1-2 times, might not repeat' case" (misreading
its own count to keep applying the heuristic), the other defers to "if a
fourth email type shows up." All four, hit or miss on the surface, treat
instance count as the actual question — never the underlying "is this
really the same knowledge" question DRY is about.

This confirms the hypothesis was right, not just plausible: rule-of-three
reasoning isn't a proxy for correct DRY judgment on this case, it's a
different heuristic entirely that happens to overlap with the correct
answer only while the instance count stays below whatever threshold the
model reaches for that run. Since the case only ever shows 2 instances,
today's benchmark structurally couldn't distinguish "the skill
understands DRY's actual boundary" from "the skill counts to three" — and
now there's direct evidence it's the latter, at least for this case
shape. Worth a genuine Case C in the real benchmark suite (not just this
exploratory check) the next time `05-dry.md` gets revisited, and probably
worth rethinking what `principles.md`'s DRY section says about the "rule
of three" itself — right now it's presented as the main operational test,
with no warning that instance-count alone doesn't distinguish real
duplication from coincidence.

### A wording fix attempt, tried and failed cleanly — worth stating plainly

Same day, restructured `principles.md`'s DRY section: moved the
knowledge question ("would a change to one require the same change to
the other, for the same reason") to the front of "How to apply it," and
explicitly demoted rule of three to a timing heuristic that only applies
once duplication is already confirmed real — with an explicit warning
that instance count alone never answers the knowledge question.

Verified against the same 3-instance scenario, 4 fresh with-skill runs:
**0/4 improved. All four hard-flagged it as a DRY violation** — worse on
the surface than the pre-fix exploratory batch (2 hard-flags, 2 soft
deferrals out of 4). None of the four transcripts show any sign of
reaching for the reordered knowledge question; all four reason about
shape and instance count exactly as before ("three near-identical
classes," "no shared abstraction," "the duplication exists today, not
'might exist later'").

Read plainly, not softened: restructuring the rule didn't move the
needle at all on this failure mode. The likely reason, on reflection —
the section's own worked "Example" paragraph is about a completely
different scenario (unmet YAGNI in build tooling, and a god-class
extraction call). There's no concrete worked example anywhere in the DRY
section showing *this* trap — three structurally identical snippets that
are still coincidentally similar, not shared knowledge. Abstract rules
about "ask if the meaning is the same" competed against a strong,
concrete pattern-match instinct ("three copies of the same shape") with
nothing equally concrete on the other side.

### Third attempt: a concrete worked counter-example — also failed

Added a second `**Example**` paragraph to the DRY section, in a
deliberately different domain from the benchmark case (three
`isEligibleFor*` checks owned by different teams, not email builders),
walking through the exact reasoning: same one-line shape, three
unrelated business rules, and why counting occurrences never settles it
even as the count grows. This was the different idea worth trying — a
worked example instead of another rule.

Reverified against the same 3-instance email-builder scenario, 4 fresh
with-skill runs (skill confirmed loaded — `tool_uses: 1` on every run):
**2 hard-flagged, 2 held back** — statistically indistinguishable from
the very first exploratory batch before any edit was made (also 2/4).
One of the two soft responses used the word "unrelated" for the first
time across every transcript collected today ("three unrelated
one-liners don't yet justify an abstraction") — the closest any response
got to the actual reasoning — but then still fell back to "add one only
when a fourth builder appears," the same count-based deferral as
everything else.

Three independent fix attempts today — an added sentence, a restructured
section, and a concrete worked example in a different domain — produced
0/4, 0/4, and 2/4 (no better than baseline) respectively. Stopping here:
three clean failures on three genuinely different approaches is itself
the finding. This isn't a wording problem in `principles.md` that a
fourth attempt is likely to crack; it reads more like a pattern-match
instinct ("N similarly-shaped snippets = duplication") that resists
in-context correction regardless of how the correction is framed. Left
as a documented, unresolved limitation, not a solved one — worth
revisiting with a different mechanism entirely (e.g. a real Case C added
to the scored benchmark suite, tested across a broader set of principle
wordings) rather than another same-day patch attempt.

## What this does and doesn't establish

- Confirms Fail Fast's fix generalizes — this was the main open question
  carried over from 2026-08-19, and it's answered: stable at N=4.
- Finds and fixes one case-file defect (`07-cqs.md` Case B) with the same
  root cause as the Fail Fast one — same day, verified.
- Investigates a CQS Case A baseline recall wobble down to real ~50%
  variance (not a systematic gap) — a working hypothesis about semantic
  vs. syntactic smells, not proven.
- Investigates a DRY Case B with-skill miss, and tries — three times — to
  fix it in `principles.md`, honestly reporting all three attempts as
  failed. The surface hit/miss tally (4/6, then 6/6 after edit #1) was
  measuring the wrong thing: nearly every run reasons via rule-of-three
  timing, not recognizing coincidental similarity. Confirmed that
  directly with a 4-run exploratory check adding a third, still-unrelated
  variant — 4/4 reasoned about instance count, none about meaning. Edit
  #2 restructured the section (knowledge question before rule of three)
  — 0/4 improved, worse than before. Edit #3 added a concrete worked
  counter-example in a different domain — 2/4, statistically the same as
  the unedited baseline. Three different approaches, three clean
  failures: this reads like a pattern-match instinct that resists
  in-context correction, not a wording gap a fourth attempt is likely to
  close. All three edits left in place (each correct on its own merits)
  but none shown to fix anything — a genuinely open, unresolved
  limitation, not a solved problem. See the report for the full,
  three-times-reversed chase.
- Does not scale N=4 to the other 17 principles — those still stand at
  N=2, per [the 2026-08-19 report](2026-08-19-principles-and-rerun.md).
