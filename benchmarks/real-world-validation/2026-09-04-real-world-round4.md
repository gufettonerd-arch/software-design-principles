## Picking the target — and a second false-positive-caller trap

The first candidate considered was a different ~10,200-line class in the same module, chosen because it exposes some inner data-layout classes that 9 other files appear to `import`. That looked like exactly what round 3 couldn't test: real, Java-level, cross-class callers. It wasn't. Checking each of the 9 files individually showed all nine **locally redeclare the same-named inner classes**, shadowing the import — so the import is dead in every single case, an artifact of the transpiler duplicating each program's copy of a shared COBOL copybook (`COPY` inlines the structure into every program at compile time; the generated Java preserved that duplication, and also emitted a spurious, unused import alongside it). This is architecturally the same trap round 3's grep-based false positives were, just manifesting as a literal, syntactically-valid, semantically-dead `import` statement instead of a string match — worth flagging because it is *harder* to catch than a grep false positive: `import` looks like real evidence of a dependency until you check whether anything in the file actually resolves to it.

With that ruled out, the round instead targeted a genuinely self-contained flow **inside** that same class: a date-arithmetic subsystem (COBOL paragraph family `DT10-*`, 14 methods, lines ~9651–10219 — the entire tail of the file) that adds N days to a date with century inference for 2-digit years, month/year rollover, and leap-year handling. Unlike almost everything else in this class, it reads and writes only its own dedicated corner of the shared `ws` object (a handful of fields under `ws.dateCalcArea`), not the dozens of unrelated fields most flows touch — the shared-global-state problem that made round 3's target resistant to a real parameterized extraction doesn't apply here. It has 3 real internal call sites (`cobol.perform(procDt10AddDays)`, confirmed via grep — genuine call sites this time, not shadowed imports) plus internal fan-in among its own sub-paragraphs. Bigger and more algorithmically real than round 3's 30-line field copy, and — unusually for this codebase — narrow enough in scope to test whether a *real* extraction (explicit parameters, an explicit return value, no shared mutable state) is achievable, not just a same-class private-method dedup.

## The task

> Extract this date-calculation subsystem into a standalone, framework-decoupled Java class — no base-class coupling, no transpiler-runtime types — that could plausibly be the first piece of an eventual full rewrite of this codebase into idiomatic Java. Since this subsystem's read/write footprint is narrowly scoped (unlike most flows in this class), a real parameterized extraction should be achievable here: use your own judgment on the exact shape. Update all 3 call sites to use the new class, preserving the exact current behavior — including the century-inference quirk, the leap-year logic, and whatever happens to the output field in the error case; read the code carefully rather than assuming. Don't touch anything else in the class.

All three sessions were fresh (no shared context), explicitly forbidden from running any `git commit`/`git push` (changes left uncommitted in their worktree; the orchestrating session verified and discarded them afterward — nothing from this exercise was merged anywhere), told verification would be best-effort since no CICS/mainframe runtime is available, and told not to ask clarifying questions.

## Session A — baseline

Fresh session, explicitly told **not** to consult any skill.

**What it did**: New standalone class (14 private helper methods, one per original sub-paragraph, operating on private instance fields — a fresh instance per call, no shared mutable state) exposing `addDays(startDate, days)` and `daysBetween(startDate, endDate)`, both returning a `Result` value carrying every field of the original output group (not just the computed date). `Bkg014.java` diff: +27/−571, at the 3 call sites plus removal of the entire 568-line original block. Added a `src/test/java` self-test (11 hand-checked cases: leap-year rollover both directions, century inference both directions, a year-boundary add, and several `daysBetween` cases) — the module has no existing test infrastructure, so this is new scaffolding, not an extension of anything already there.

Verification: found and used the same real classpath source C found in round 3 (a prior build's compiled classes plus the runtime's dependency jars, present in the checkout from earlier work) for a genuine dependency-complete compile — clean. Ran the self-test directly with `javac`/`java` (no framework needed since the new class has zero dependencies) — 11/11 passed. Caught and fixed its own line-ending mistake mid-task (an edit tool had silently converted the file from CRLF to LF; noticed via an inflated diff stat, restored CRLF, re-verified).

**Anything notable**: Chose to write back all four output-group fields on every call (not just the computed date), reasoning from a caller elsewhere in the class that re-reads more than the primary output field after invoking this flow. Independently found and flagged that the same date-arithmetic paragraph family exists as private, byte-for-byte copies in roughly 170 *other* transpiled files across the codebase (the same COBOL-copybook-duplication pattern behind this round's false-positive-caller finding above) — correctly left all 170 untouched as out of scope, but flagged it as a real, large future deduplication opportunity for the "pure Java" rewrite. Preserved the century-inference quirk and the non-Gregorian leap-year rule exactly, with tests pinning both down explicitly rather than "fixing" them.

## Session B — with-skill

Fresh session, told to use `software-design-principles` and follow the god-class-extraction playbook. (This session's task additionally noted, compared to a prior round's more globally-coupled target in this same codebase, that this flow's narrow footprint should let the playbook's usual parameterization/Service/coverage steps apply fully rather than needing the same workarounds.)

**What it did**: New standalone class, 313 lines, same shape — private per-call engine, zero shared state, `addDays`/`daysBetween` entry points returning an immutable `DateggResult` value object whose accessors throw a specific exception if called on an error result rather than returning a misleading default. `Bkg014.java` diff: +19/−565. Notably tighter than A: merged two pairs of near-identical original sub-paragraphs (a leap/non-leap table variant that differed only in which lookup table they read) into one parameterized helper, and factored the duplicated date-validation logic (used once for the input date, once for a second date-comparison paragraph) into a single `parseDate` helper — real, behavior-preserving consolidation beyond a 1:1 port.

Verification: independently found the same real classpath, clean dependency-complete compile. Wrote and ran a 15-case self-test (kept outside the repo, in scratch space, rather than adding test scaffolding to a module with no existing test setup — a deliberate scope call, explained rather than silently done). Went a level deeper than the other two sessions on one point: used bytecode inspection to check whether the underlying field-storage type silently truncates on overflow, because one intermediate calculation can transiently exceed its original 3-digit field's declared width before the first correction pass runs. Could not fully resolve the question in the time available, flagged it explicitly as an open, unverified risk (rather than silently guessing either way), and noted that no real call site's actual inputs get anywhere near the boundary that would expose it.

**Did it follow the playbook's actual steps?** Engaged with all thirteen explicitly. The most substantive difference from a prior round's report on this same codebase: Steps 8 (Service/Value Object), 10 (no shared mutable state), and 11 (real test coverage) were fully applicable and applied here, where a previous, more globally-coupled flow in this same class couldn't support them — the session explicitly named this contrast, treating the narrower flow as the reason those steps became achievable rather than assuming the playbook simply "worked better this time."

**Anything notable**: Same error-handling fidelity as the other two (see Comparison). Correctly identified that the original's paragraph-internal defensive is-this-actually-a-digit checks become vacuously true once the new API takes a typed integer parameter instead of a raw field, and dropped them with a documented rationale rather than mechanically porting dead checks.

## Comparison — and independent verification

The orchestrating session did not just collect these three reports — it independently re-read the *original*, pre-extraction source for the error-handling paragraph before trusting any of the three accounts, and independently re-compiled all three sessions' final `Bkg014.java` plus their new class against the same real dependency classpath they each found on their own. Both checks are reported here because a "the sessions verified it" claim isn't the same as "it's verified."

- **Error-case fidelity, checked against the original source directly**: the original error paragraph does exactly one thing — zero the *entire* output-field group, not just the computed-result field — before setting the error flag. On the success path, only the single computed-result field is written; the input fields are never touched. All three sessions reproduced this exactly on the error path. On the success path, B and C write back only the computed field (matching the original precisely); A writes back all four fields, including the two that are already unchanged — reasoning explicitly from a caller that reads the wider group after invoking this flow. Read against the actual original code, A's extra writes are redundant, not wrong: the values it writes back on success are identical to what was already there, so there is no observable behavior difference between the three, just a difference in how defensively each session modeled the contract. Recorded as a real, meaningful three-way agreement once checked, not merely a self-reported one.
- **All three compile cleanly against the real dependency classpath.** Confirmed independently, not just accepted from the reports — reproducing each session's compile initially failed for reasons on the verifying side (an overly broad file glob the first time, a classpath-construction mistake the second), both diagnosed and fixed before concluding the code was clean. Worth recording as a caution about this kind of exercise generally: a failed *reproduction* of a verification claim is not the same as a *refuted* claim, and is at least as likely to be a bug in the check as in the code being checked.
- **All three converged on the same core shape** — a small, dependency-free class; a fresh, non-shared per-call working area instead of the class-wide `ws` object; an explicit, typed result instead of reading scattered fields back out of shared state — on a task that, unlike round 3's, genuinely allowed that shape. That convergence is itself informative: given a flow narrow enough to make a real extraction possible, baseline, skill-guided, and unprompted sessions all found the same "real Service/Value-Object shape," not just the same "smallest safe change" round 3 converged on. The skill didn't need to argue anyone into it.
- **Real differences, ranked by how much they'd matter to a reviewer**: (1) B's flagged-but-unresolved storage-truncation question — a genuine open technical risk none of the other two even considered, raised responsibly rather than either ignored or guessed at; (2) B's actual behavior-preserving consolidation of two near-duplicate sub-paragraph pairs, a real simplification beyond a 1:1 port that A and C didn't attempt; (3) test thoroughness — C's 16 cases were the most complete, including two neither A's 11 nor B's 15 covered; (4) the redundant-but-harmless extra field-writes in A's success path, discussed above.
- Did the skill catch something real the other two missed? Only the truncation question is a strong candidate, and it's explicitly unresolved, not a caught bug — a good-faith flag, not a finding.
- Did the skill add ceremony the others correctly skipped? No — B's test lived outside the repo exactly as A's and C's did, for the same stated reason (no test infrastructure exists in this module), and its consolidation of the duplicate sub-paragraphs is a genuine simplification, not unrequested structure.

## Verdict

Would trust this again, and it's the clearer confirmation of the two rounds run on this codebase: given a real flow narrow enough in scope to allow it, all three sessions — with or without the skill — independently reach for the same properly-parameterized, dependency-free extraction shape that round 3's target structurally couldn't support, and all three hold up under independent re-verification against the original source and a real compile, not just their own self-reports. The measurable differences this round were not about correctness (none was found, on real, careful checking) but about thoroughness and honesty under uncertainty — test coverage breadth, a consolidation pass beyond the minimum, and a flagged-not-guessed open question — which matches this project's rounds 1–2 finding on a completely different codebase: the skill's most consistent, repeatable effect across four rounds now is making already-good judgment legible and checkable, not correcting bad judgment a careful baseline would have gotten wrong anyway. The other standing finding from this round is procedural, for whoever runs a fifth: an `import` in generated code is not proof of a real dependency in this codebase any more than a grep hit was in round 2 — check what actually resolves before designing a task around it — and a verification claim (compile passed, tests passed) is worth an independent, careful reproduction attempt before it goes in a report, because the reproduction itself is exactly as fallible as the thing it's checking.
